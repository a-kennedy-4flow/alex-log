# Testing

## The corpus hiding in the PDF

The standard was written to teach, so almost every rule and almost every dictionary entry comes
with a worked pair: a compliant sentence and the non-compliant sentence it replaces. Counted in
the extraction:

| Source | Count |
| --- | --- |
| Dictionary entries with an STE example | 2176 |
| Dictionary entries with a non-STE example | 1377 |
| `Non-STE:` labelled sentences in Part 1 | 102 |
| `STE:` labelled sentences in Part 1 | 284 |

Roughly **3900 labelled sentences from the authority itself**, and the labels are exactly the
ones the checker needs to reproduce. This is the project's single most valuable asset and it
should drive development rather than be added at the end.

Two assertion families fall straight out:

- **Negative cases.** A dictionary non-STE example for a non-approved headword must produce at
  least one finding on that word, and the finding's rule must be the one the entry illustrates
  (usually 1.1 or 1.2). A Part 1 `Non-STE:` sentence must produce a finding for the rule under
  whose heading it appears.
- **Positive cases.** An STE example must produce **zero** findings from any implemented rule.
  This is the harsher and more useful half: it is what catches false positives, and false
  positives are what get a controlled-language checker switched off.

The corpus caveat from [04-data-pipeline.md](04-data-pipeline.md) applies — the examples need
cleaning before they are ground truth. Budget for it; the whole test strategy rests on it.

## Corpus format

`tests/corpus/*.jsonl`, one case per line, generated by `cargo xtask extract-corpus` and
diffable in review:

```json
{"id":"dict/abaft/prep/non-ste/0","text":"The control unit is installed abaft the flight compartment.",
 "verdict":"violates","rules":["1.1"],"word":"abaft","origin":"part2:2-1-A2","reviewed":true}
{"id":"dict/abaft/prep/ste/0","text":"The control unit is installed aft of the flight compartment.",
 "verdict":"clean","origin":"part2:2-1-A2","reviewed":true}
{"id":"part1/1.2/non-ste/0","text":"Test the system for leaks.",
 "verdict":"violates","rules":["1.2"],"origin":"part1:1-1-2","reviewed":true}
```

`reviewed` marks cases a human has confirmed the extractor got right. Unreviewed cases run in a
separate advisory lane so a bad extraction cannot fail the build, and the reviewed fraction is
itself a tracked number.

Three subtleties the harness must handle honestly:

- **Positive cases only assert about implemented rules.** An STE example may still trip a rule
  the engine has not got right yet. Filter by the rule registry so adding a rule cannot
  retroactively break unrelated cases without the diff showing it.
- **Negative cases assert "at least this finding", not "exactly".** A non-STE sentence often
  breaks several rules at once; `Test the system for leaks.` violates 1.2 and arguably 3.7.
- **Some positive cases will legitimately fail** because they demonstrate a rule in isolation
  and are not fully compliant otherwise. Those get an `expect_findings` allowlist with a written
  reason, reviewed like any other exception.

## Headline metrics

Reported by `cargo xtask report` and tracked per milestone, because "the tests pass" says
nothing about coverage of a 53-rule standard:

| Metric | Meaning |
| --- | --- |
| **Recall** | % of negative cases where the expected rule fired |
| **Precision proxy** | % of positive cases with zero findings |
| **Tagger accuracy** | % of dictionary examples where the headword's surviving readings include its declared part of speech ([03-ambiguity.md](03-ambiguity.md)) |
| **Rule coverage** | implemented ÷ decidable, by tier |
| **Corpus review** | % of corpus cases with `reviewed: true` |

The precision proxy is the one to watch. Recall is easy to buy by making rules aggressive, and
every milestone will be tempted to.

## The rest of the pyramid

**Per-rule unit tests** in each rule module, in the doctest style the Elixir prototype uses —
the examples in the module documentation *are* the tests. Worth reproducing in Rust with
doctests on the rule's public entry point, because it keeps the specification, the examples,
and the code in one file.

**Word-count tests, separately from any rule.** Rules 8.4–8.7 define a counting function that
2.1, 5.1, and 6.3 all consume, and a mistake there mis-scores three rules without any test
failing where the bug is. The standard supplies its own worked examples — `The spar box has
twenty-one ribs.` is six words — and each element of 8.6 gets direct coverage: numbers, numbers
with units, abbreviations, alphanumeric identifiers, quoted text, titles and labels, proper
nouns, hyphenated words, parenthesized text, and the vertical-list colon.

**Rule interaction tests.** Some rules genuinely pull against each other and the resolutions are
design decisions that must not silently regress:

- 1.2 forces `Do the leak test of the system` (`test` is not an approved verb) while 3.7 prefers a
  verb over a noun for an action. 3.7 must not fire here.
- 3.2 bans most verb forms while 3.3 licenses the past participle as an adjective. 3.2 must not
  fire on a licensed participle.
- 3.5 bans `-ing` forms except inside a technical noun. With `operating rod` in the glossary, no
  finding; without it, a finding.
- 8.7 makes a hyphenated word one word, which is precisely the escape hatch 2.2 offers for a
  multi-word noun over the 2.1 limit. Hyphenating must actually change the 2.1 verdict.

**Property tests** (`proptest`) on the analysis layers, where the invariants are strong:

- Tokenization never panics and never produces a span outside the source or off a UTF-8
  boundary — worth fuzzing too (`cargo-fuzz`), since the tokenizer is the one component that
  sees arbitrary bytes.
- Analysis is idempotent, and findings are deterministic: two runs on the same input produce
  byte-identical output. Non-negotiable, since snapshot tests and CI gates both depend on it.
- Concatenating two paragraphs does not change the findings within either.
- Sentence spans partition the block's text; token spans are non-overlapping and ordered.
- No finding has an empty span, and every span lies inside the block that produced it — the
  cheapest guard against `SourceMap` bugs, which are otherwise invisible until an editor
  highlights the wrong word.

**Snapshot tests** (`insta`) over whole formatted reports, to catch changes in message wording,
ordering, and severity that unit tests miss.

**Differential test against the Elixir prototype** while porting rule 1.1. Both read the same
`dictionary.json`, so run both over the corpus and diff the findings. A free oracle that exists
only during M2 — use it then.

**Benchmarks** (`criterion`) with targets set early, since the LSP use case is what makes them
matter:

- L0–L4 throughput ≥ 10 MB/s single-threaded.
- Full analysis with all layers ≥ 1 MB/s single-threaded.
- Incremental re-check of an edited paragraph < 20 ms in a 500-page document. This is the
  number that decides whether the LSP feels alive, and it is a constraint on the architecture,
  not a late optimization — it is why L1 blocks are the unit of invalidation.

## Real-document testing

The PDF corpus is uniform, short, and stylistically narrow; it will flatter the checker. Before
believing any precision number, run over a real document set — the standard's own Part 1 prose
is a fair first target, since Issue 9 states that "all texts in part 1 comply as much as
possible with STE". Findings there are either real bugs in the checker or genuinely interesting.

That test is available from M1 and costs nothing. It is also the most honest feedback the
project will get before a writer uses it in anger.
