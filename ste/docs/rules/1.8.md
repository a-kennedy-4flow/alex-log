# Rule 1.8 — Technical nouns of your company

**Statement** (Issue 9, page 1-1-11)
> Use technical nouns that are approved in your company, industry, or subject
> field.

- **Applies to:** every technical noun of the text.
- **Needs:** glossary, with a preferred term and its rejected synonyms.
- **Decidable:** yes, when the glossary records which term is preferred.
- **Code:** not implemented.

## Discrete form

```
check(text, glossary G) -> [finding]

for each technical noun n of text:
    if G marks n as preferred:                       continue
    if G marks n as a rejected synonym of term t:    finding(n, use: t)
    if G does not list n at all:                     finding(n, reason: :not_in_glossary)

pass = findings == []
```

The rule needs a glossary shape that rule 1.5 does not: not only "is this a
technical noun" but "is this **the** technical noun". A minimal entry is
`%{term: "actuator", synonyms: ["servo control unit", "control unit"], categories: [6]}`.

## Examples

| Verdict | Text | Why |
| --- | --- | --- |
| pass | `The front panel of the phone has a touchscreen and a home button.` | "touchscreen" and "home button" are the approved terms |
| fail | `Disconnect the servo control unit from the test rig.` | the approved term is "actuator" |

## Out of scope

- Whether the term belongs to a category at all — rule 1.5.
- Naming the same item two ways inside one document — rule 1.11, which is the
  document-level form of this rule.
- Wording that changes between work steps — rule 9.4.

## Notes

- Usually such technical nouns come from official parts information and company
  documentation, so the glossary should be generated from the parts catalog or
  terminology database rather than written by hand.
- Without a glossary this rule cannot report anything useful, so a checker should
  say "not checked" rather than "pass" when no glossary is configured.
